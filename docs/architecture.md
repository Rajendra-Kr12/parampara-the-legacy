# Architecture: Parampara

## Status

Stack direction accepted 2026-10-10 (D-014, D-015). Workspace tooling, CI, and `packages/backend` exist; no web or mobile app yet. The toolchain versions are pinned and confirmed in `docs/decision-log.md` (D-032 to D-040); the web and mobile versions arrive with steps 3 and 4. The open items at the end are confirmed as those steps ship.

## Architecture principles

- One canonical person identity, multiple relationship edges.
- Domain rules independent of UI, Convex, and AI providers.
- Authorization enforced server-side in Convex functions.
- Explicit workflow states for claims, reviews, disputes, and publication.
- Sensitive changes are auditable and transactionally consistent.
- Media is private by default.
- One set of business rules shared by web, iOS, and Android.
- External AI is optional and never required for core family operations.

## Selected stack

| Concern | Choice | Why |
|---|---|---|
| Monorepo | Turborepo + pnpm workspaces | Web and mobile built simultaneously while sharing domain code |
| Web | Next.js (App Router) + TypeScript | Mature web framework, good web UX and accessibility |
| Mobile | Expo (React Native) + Expo Router + EAS Build | One codebase for iOS and Android, managed native builds |
| Backend and database | Convex | TypeScript end to end, transactional mutations, realtime sync, generated typed API for both apps, no ORM needed, open-source self-host option |
| Auth | Clerk | Free tier covers 50,000 monthly retained users (Feb 2026); SDKs for Next.js and Expo; official Convex integration |
| Media | Cloudflare R2 behind a storage adapter | ~$0.015/GB-month, no egress fees, S3-compatible so B2 or S3 can replace it by configuration |
| PR review | Greptile + Codex adversarial review | Greptile on every PR; Codex before shipment |
| CI | GitHub Actions | Format, lint, typecheck, test, build on every PR; plus a non-blocking Fallow code-health report (D-040) |

Clerk and Greptile also appear in `adrianhajdin/llm-arena`; they were chosen here on their own merits (D-021). llm-arena's Prisma, PostHog, and Arcjet choices were not adopted.

### What the shared packages are

- `packages/domain`: pure TypeScript types and rules: claim states, reviewer eligibility, approval thresholds, dispute timers. No Convex or UI imports, so it is unit-testable and reusable everywhere.
- `packages/kinship-engine`: pure TypeScript that walks relationship paths and returns valid kinship terms (for example father's sister = Atta/Menatta) for a locale, with paternal-side default and viewer preference. Web, mobile, and backend show the same label because they run the same code.
- `packages/validation`: shared input schemas (for example name required, DOB exact or year-only, address rules) used by forms on both clients and mirrored by Convex argument validators.
- `packages/backend`: the Convex project (schema, queries, mutations, actions). Its generated `api` object is the typed API client for both apps, so no separate API-client package is needed.

## Media storage

Photos and audio never live in the database. Convex stores metadata (owner, subject, permissions, R2 object key). Uploads and downloads use short-lived presigned R2 URLs generated by Convex actions after an authorization check.

- Resize images on the client to display sizes before upload; keep originals only where the product needs them.
- Back up R2 to a second provider (Backblaze B2 candidate) once real data exists.

Rough storage cost at ~15 GB of media per family (verify current prices):

| Families | Media | R2 | Convex file storage | Supabase storage |
|---|---|---|---|---|
| 100 | ~1.5 TB | ~$22/mo, no egress | ~$42/mo + $25 plan | ~$29/mo + $25 plan + egress |
| 1,000 | ~15 TB | ~$225/mo | ~$450/mo + plan | ~$315/mo + plan + egress |

Family metadata (people, edges, claims, stories) is small: a few MB per family, well within Convex's free 0.5 GB at first and the Professional plan's 50 GB later.

## Alternatives considered

- **Supabase (Postgres)**: SQL recursive queries and row-level security are strong; free projects pause after a week of inactivity; Pro plan includes 8 GB database. Viable fallback if Convex limits bite.
- **Neon Postgres + Drizzle or Prisma**: ORMs are free libraries; more plumbing for realtime and auth.
- **Firebase**: strong mobile SDKs, but Firestore makes the relationship graph and approval transactions harder.
- **AWS S3**: richest features but ~$0.09/GB egress and no lasting free tier for new accounts since July 2025.
- **Cloudinary**: good image transforms, but sends private family photos through a third-party media pipeline; not adopted.

## Logical layers

1. Client apps (`apps/web`, `apps/mobile`): screens, navigation, local validation, accessibility.
2. Convex functions: authorization-aware queries, mutations, actions.
3. Domain packages: relationship graph rules, kinship calculation, claim transitions, reviewer eligibility, dispute rules.
4. Persistence: Convex tables, indexes, audit events.
5. Media: R2 via a storage adapter, signed access, lifecycle and deletion.
6. Background work: Convex scheduled functions and crons for imports, media processing, dispute deadlines, notifications.
7. External integrations: email/SMS delivery, optional AI services.

## Data integrity

- One Convex mutation for approval + status change + audit record.
- Convex mutations are serializable transactions; still design for conflicting proposals at the domain level.
- Keep history for approved sensitive fields; no single `verified` boolean.
- Keep original imported values and import provenance.
- Model failed and pending workflow states explicitly.
- Validate graph constraints and detect invalid cycles where the relationship type requires it.
- Add indexes for every query path; Convex bills for documents scanned.

## Security boundaries

- Every public Convex function checks the Clerk identity from `ctx.auth`; privileged operations use internal functions.
- Client-supplied role, relationship, reviewer eligibility, and consent flags are never trusted.
- Secrets live in Convex environment variables, Vercel/EAS secrets, or gitignored `.env.local`. Never in `EXPO_PUBLIC_*` or `NEXT_PUBLIC_*` variables, which ship to clients.
- Verify Clerk webhook signatures.
- AI output is untrusted input and cannot directly write approved family facts.
- Admin tools use least privilege and are audited.

## Open items

- Client apps: `apps/web` and `apps/mobile` do not exist (Feature 1 steps 3 and 4). Next.js, Expo SDK, and React are not pinned, and the Expo SDK choice, the mobile sign-in flow, and where the simulator and emulator proof runs are still undecided (D-038).
- Sign-in is in progress. Nothing has been signed in against a real Clerk instance or Convex deployment, so no end-to-end proof path exists yet. The Clerk development app and the Convex development project both exist, and the Clerk issuer domain is already set in the Convex development deployment (owner-confirmed 2026-10-12, D-038). The sign-in proof itself is still to come.
- Test stack beyond the shared packages and Convex: Playwright with `@clerk/testing` for web, `jest-expo` for mobile components, Maestro for mobile end to end (D-036). No coverage threshold.
- CI hardening: `protect-main` has no required status checks, repository-wide action SHA pinning is off, and there is no mobile E2E workflow or Turbo remote cache (D-037). These change shared settings and need owner approval.
- Convex codegen drift check: `convex codegen` needs `CONVEX_DEPLOYMENT`, so a drift job is still to be designed.
- i18n approach shared by Next.js and Expo, which D-025 requires Feature 1 to pick; CI should fail on a missing translation key.
- Styling approach shared across web and mobile (for example NativeWind or Tamagui).
- Data residency: confirm Convex and R2 regions and obligations under India's DPDP Act before storing real data.
- Clerk SMS OTP cost and availability for Indian numbers; email-link limits on Expo native.
- Notification provider (email/SMS/push).
- Analytics: deferred; must avoid personal data.
